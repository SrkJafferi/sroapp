# Phase 2A database security validation

Run from the monorepo root:

```powershell
pnpm check:db
pnpm typecheck:db
```

`security.test.ts` preserves the original 48 scenarios. `readiness.test.ts` adds 22 review regressions and catalog/manifest checks. Both replay the three candidate migrations into disposable PostgreSQL 17.5 WASM databases. They do not read environment files, accept a remote URL, create real Auth users or invoke Supabase. Fixture identities and medical content are fictional.

The lock-boundary regressions deliberately replace the **local test database's** `lock_doctor` definition to revoke authority after its advisory-lock call. They prove that a second authorization check exists and denies changed authority. They do **not** exercise simultaneous backends, PostgreSQL wait queues, JWT validation, PostgREST transactions or cancellation of an already-running statement.

## Native/PostgREST evidence and remaining limits

The [Phase 2A.5 final report](../../docs/phase2a5-final-validation.md) records actual approved staging results: PostgreSQL 17.11, 95 HTTP cases, 22 standard independent-connection cases, a timezone/new-assignment regression and seven timezone/DST HTTP cases. The `staging-*.mjs` scripts enforce the exact approved staging target and never load application environment files. Generated staging credentials were exposed through Base64 transcript transport and require approved rotation before reuse. Do not rerun the fixtures against retained data or the protected project.

The broader matrix below is a test plan, not a claim that every load/disconnect/lifecycle scenario was executed. Use the final report's explicit case inventory for pass evidence. The older `booking-race.spec` isolationtester file itself remains unexecuted; actual concurrency evidence came from native client backends and observed `pg_blocking_pids`, not that specification or the WASM runner.

Use an independently approved, disposable Supabase-compatible environment with PostgreSQL 17.11 and actual Auth/PostgREST. Never use `jyigxpjvygvtvcypujel` for destructive fixture/race testing. Use a new fixture database for each native isolation specification; the supplied `booking-race.spec` commits one booking and does not clean it up. Do not convert it into a cleanup script against retained clinical data.

| ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Reschedule proposal versus another booking, and reschedule approval versus cancellation                                                  | No lost original hold, no duplicate active hold, no partial status/charge/audit changes. Exercise commit and rollback orderings.                                                                                           |
| Leave versus booking/check-in/start/signing                                                                                              | Whichever wins the Doctor lock determines the legal outcome; no booking in active leave; checked-in/active visits reject overlapping leave; pending visits are flagged without releasing unresolved holds.                 |
| Schedule/break/duration/assignment edits versus booking or proposal approval                                                             | Same Doctor lock participates; capacity-reducing edit is rejected if a future hold wins, or booking sees the committed edit and is rejected. Include a newly inserted schedule/assignment and edits spanning many Doctors. |
| Branch timezone edit versus booking and new Doctor/branch assignment                                                                     | No reservation is accepted using a stale branch timezone. Document MVCC/in-flight statement behavior; revocation does not magically cancel work already authorized and committed.           |
| Grant/revoke race and expiry during an in-flight request                                                                                 | A new request cannot retain expired/revoked access; row locking and audit entries remain atomic. Test transaction-time `now()` expiry semantics and request timeouts.                                                      |
| Cancelled/disconnected request or forced constraint failure                                                                              | No partial appointment, encounter, Rx, reservation, notification or audit transaction survives.                                                                                                                            |

With real ordinary user JWTs, exercise all eight RPCs and all 34 tables using valid Admin/assigned Doctor/additional clinician/Patient personas plus wrong-branch, wrong-organization, unprovisioned, missing-subject, expired and invalid-signature tokens. Check PostgREST embedding/filtering/upsert requests, direct writes/TRUNCATE denial, notification column-only updates, returned row shapes, SQLSTATE-to-HTTP mappings, PUBLIC/anon/service-role function ACLs and the absence of `clinic_private` from exposed schemas. Test service-role provisioning independently; a service key is intentionally denied clinical/workflow tables and the eight RPCs.

No real JWT or native multi-connection result is currently claimed. Keep logs free of tokens, API keys and patient content. Record versions, identities as fictional labels, SQLSTATE/HTTP outcomes, lock wait/timeout behavior and the exact migration hashes in the staging report.
